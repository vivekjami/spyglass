Architecture

What I built, and what TrueForge already does

  • Built: a Rust engine — ingest, Drain template mining keyed by log level, novelty scoring, guarded changepoints with deploy correlation, a linear ranker, bounded bundles
  • Built: the causal check and the write plane (propose / gated rollback)
  • Used as-is: TrueForge runs the agent loop, sub-agents, the approval gate and the sandbox

What the agent actually sees

One call replaces paging the logs

events → evidence items, in 4.7 kB
  • What is new — the novel ERROR template, with its stack
  • When it changed — the changepoint, +0.6 s after D-2
  • What was deployed — and which deploy precedes which change
  • Every item: an evidence id, a digest, and engine_latency_ms
Bounded by construction — the response cannot exceed 8 kB, and it says what it did not show you.

The experiment

Same model. Same harness. Only the evidence varies.

  • 3 conditions — raw tools · Spyglass · Spyglass minus novelty
  • 4 scenarios × 3 repeats = 36 runs, 36 valid
  • Ground truth pre-registered before the first run
  • Scoring is mechanical — a fenced verdict block plus an evidence-id join. No LLM judge
  • Every run committed, failures included
The four scenarios S1 a deploy regression with a stack trace · S2 a config-only release → latency cascade · S3 redis full, no change event · S6 an unobserved vendor, no cause in the telemetry
Harness context-management pinned off in every condition, so the harness does no shaping of its own on the control group (ADR-016).

Correct refusal0/31/33/3

An unobserved vendor degrades. Latency only, no error, no change event — and a benign deploy 130 s earlier as bait. Take novelty away and the system refuses correctly every time. Leave it in and it hands the model a story: two of three runs rolled back the innocent deploy. On the safety floor my full system was the worst of the three.

More evidence made the agent act. That is a negative result about my own thesis — produced by my own benchmark, and committed with the runs that show it.
What it cost me — and the fix

Two gaps, recorded rather than quietly patched

  • Verification judged the wrong metric. It reads the 5xx share only — so after a wrong rollback on a latency incident it reported "recovered" while p95 was still above 5 s. Fix: judge the alert's own metric, or refuse.
  • No mechanical evidence floor on proposals. Nothing stops a rollback whose cited evidence contains no deploy-correlated change. Fix: the deployer refuses it before a human ever sees it — which on S6 turns two wrong actions into refusals.
Both were found after the matrix ran. Patching and re-running would have produced a nicer table and a worse result. The matrix stays the matrix; the gaps are written down in the phase record with the runs that exposed them.
Limits & what is next

What this does not show

  • n = 3 · one model · one incident domain
  • Scenarios authored by the same person who built the system
  • The harness sandbox never executed a command — diagnosed, symmetric across conditions
  • The gate was auto-approved in the matrix, so "wrong action" means "wrong proposal"
  • Next: the two fixes above, then calibrate novelty against S6
  • Widen the corpus — S4 drift, S5 one-replica; a second model
  • Then: agent-session forensics — point the same engine at TrueForge's own session logs to diagnose other agents' loops and token burns
Deliberately not claimed: whether the advantage survives better models. The pre-registered split prediction is that the accuracy gap shrinks while the token gap persists. Untested.
